# Key Decisions

| Date | Decision | Overrides |
| --- | --- | --- |
| 2026-10-08 | The project management app package is `apps/manage`, deployed at `app.whitepointsurvey.com`. | Any earlier `apps/app` naming. |
| 2026-10-08 | V4 is used as a behavior reference and split by product purpose into main, docs, manage, payment, API, and shared packages. | V4's `sites` and `cfdg` package layout. |
| 2026-10-08 | Clerk provides authentication and session identity only. Northstar stores users, roles, and permissions internally; the API authorizes requests from those records and denies access when no internal user or permission is assigned. | Clerk role bundles; V4 Microsoft Entra authentication and group checks. |
| 2026-10-08 | V5 starts from a schema-only D1 baseline; V4 rows and identifiers are not imported. | V4 snapshot data. |
| 2026-10-08 | Northstar client, project, task, and user/role records are first-party D1 records; QBO IDs and sync outcomes are attached references, and local saves complete before outbound sync. | V4's QBO customer mirror as the management system of record. |
| 2026-10-08 | Public invoice links and payment returns use `payment.whitepointsurvey.com`; staff invoice and QuickBooks links use `app.whitepointsurvey.com`. | V4's shared docs host for public payments and staff workflows. |
| 2026-10-08 | API clients use `https://api.whitepointsurvey.com/v5` as the base and omit `api` from route paths; API categories identify feature areas such as `identity`, `records`, and `invoices`. | Legacy `/api/...` and `/v1/...` route prefixes. |
| 2026-10-08 | Front-end apps use light color mode only; GIS is owned by `apps/manage`, while `apps/docs` redirects legacy GIS URLs to the management app. | Legacy dark/auto color mode and duplicated GIS screens in docs. |
| 2026-10-08 | Shared application chrome, sidebar state, auth prompts, error pages, GIS disclaimer, and API request/favorites behavior belong in `@whitepoint/ui` or `@whitepoint/utils`; apps provide only app-specific configuration and adapters. | Duplicated app-local implementations. |
| 2026-10-09 | The first API reset uses a clean D1 migration baseline and exposes only health, identity/users, clients/contacts, projects, search, and QBO connection/sync routes under `/v5`; unsupported API route families are removed without a version bump. | Mixed V4/Northstar routes and migrations. |
| 2026-10-09 | Clerk and QBO operations follow local-save-first sync; each record stores provider status/error and has a retry path where appropriate. Clerk owns authentication identity, while D1 remains the authorization source of truth. | Provider-first saves and API-key authentication. |
| 2026-10-09 | The initial local D1 administrator is the supplied Clerk account for `nwhite@whitepointsurvey.com`, assigned the built-in super-administrator role; fresh baseline databases initialize this user directly. | The interactive one-time setup path for an empty database. |
| 2026-10-09 | Self-hosted D1 authentication replaces Clerk. The API owns staff credentials, revocable sessions, and permissions; Manage and protected Docs pages share an API-hosted session cookie. Staff must enroll TOTP or a user-verified passkey. | The earlier Clerk identity, synchronization, and seeded Clerk-account decisions. |
| 2026-10-09 | The seeded `nwhite@whitepointsurvey.com` administrator is claimed once with a Worker bootstrap secret and then enrolls a second factor. Brevo sends staff invitation and password-reset links. | The prior Clerk-linked setup and provider-sync workflow. |
| 2026-10-09 | Every staff account must confirm TOTP during setup before protected access. Recovery codes are issued immediately after TOTP confirmation; a passkey can be added afterward as an optional sign-in method. | The earlier choice of TOTP or a passkey during enrollment. |
| 2026-10-09 | Administrator authenticator enrollment generates and presents the QR code and manual key by default, before requesting a verification code. | The earlier verification-first setup layout and manual QR generation step. |
| 2026-10-09 | The login page shows first administrator setup only while the API reports that initial setup is required. | An always-visible first administrator setup link. |
| 2026-10-09 | Shared form controls live under `packages/ui/src/input` and are exported through `@whitepoint/ui/input`; text controls use native value events, selection controls use string values, and each supports controlled or uncontrolled state. Existing app-facing names remain exported through adapters or retained legacy controls. | The deleted `src/input/inputs` implementation as the input source of truth. |
| 2026-10-09 | The six-digit authenticator input is a shared `OTPInput` in `packages/ui/src/input`. Staff sign-in offers a separate recovery-code field because recovery codes are not six-digit OTPs. | The local OTP implementation in `staffAuth.tsx`. |
| 2026-10-09 | QBO OAuth callbacks redirect to the configured Manage app with a short result code; Manage reopens QuickBooks settings and shows the outcome. Authorization codes stay out of Manage URLs. | Returning callback JSON directly to the browser. |
| 2026-10-11 | Manage administration uses `/settings`, `/settings/users`, `/settings/roles`, and `/settings/qbo` with one staged save per page and a navigation warning for unsaved edits. QBO OAuth returns to `/settings/qbo`. | The combined `/settings/access` page and QBO settings modal. |
| 2026-10-11 | Company settings store invoice and project number templates with `{YY}`, `{MM}`, and a one-to-ten-digit sequence token; each sequence has its own yearly reset setting. Projects receive server-generated numbers with an optional override. Invoice numbering awaits the V5 invoice workflow. Rectangular and square logos are stored in R2 but are not yet applied to app branding. | Manually required project numbers and bundled-only logo settings. |
| 2026-10-11 | Active client and project records use singular Manage routes and one revision-checked save for each record's editable tabs. Both open read-only, and copied records receive new local identifiers and numbers. Clients require a name, address, and point-of-contact; projects require a name, scope, active client, its point-of-contact, and an active internal PM. New projects start as opportunities. | The old list and quick-create pages and their duplicate page models. |
| 2026-10-11 | Client numbers use an independent configurable sequence, default `C-{####}` without yearly reset. Local D1 remains authoritative; QuickBooks clients are top-level customers and projects are child customers. Moving a project to a new client stores the former child link in history, clears the active link, and creates a new child after the local save. No QuickBooks delete is issued. | Reusing a moved project's former QuickBooks child and manually assigned client numbers. |
| 2026-10-11 | Client documents are protected R2 objects with D1 metadata. Staged uploads join the record's visible Save and are cleaned up if the D1 batch fails. Project actual costs and invoice references are read-only source-linked values; staff may edit contract price and budget with financial permission. | Standalone document saves and manually edited actual costs or invoice references. |
| 2026-10-11 | Manage's top bar uses `GlobalSearch` (Northstar-style dropdown combobox (queries only on Enter, never while typing) over the existing `GET /search` API, Ctrl/Cmd+K, grouped results, View all -> `/search`). Northstar's inactive-record toggle and `/search/preview` API are not ported. | The plain submit-only search form. |
| 2026-10-21 | Timesheets use Monday-Sunday weeks, one approval by any manager in the reporting chain, manager-controlled reopening, and explicit zero-hour submissions. Submitted entries snapshot hourly actual cost and pay-table charged value; only approved time-and-materials entries enter the future invoice pool. | Entry-level approval flags and live recalculation of historical rates. |
| 2026-10-21 | Timesheets open on a list of weeks. Each week has its own project-by-day summary table with totals at the bottom, per-cell entry creation, and click-to-edit draft time. Staff review and the invoice pool have separate pages. | The combined Timesheets page with a flat entry list. |
| 2026-10-21 | Staff enter and view rates, pay, and project amounts as decimal dollars; API contracts and D1 continue to use integer cents. | Raw cent amounts in editable money fields. |
| 2026-10-21 | Each saved project has a read-only Time entries tab showing all related draft, submitted, and approved entries. Project viewers see hours and work notes; cost and charged values require project financial and timesheet rate visibility. | Timesheet entries being visible only from weekly timesheets. |
| 2026-10-21 | User Management retains its bulk Save editor and links each saved user to a read-only, tabbed detail page at `/settings/users/:id`. The detail API returns basic fields to `users.view` and includes pay and billing fields only with `timesheets.rates.view`. | Viewing every user's details only through the bulk editor. |
| 2026-10-21 | `/settings/users` is a basic searchable user directory. Selecting a user opens the read-only `/settings/users/:id` tabs. Bulk user administration remains on `/settings/users/manage`, with its single Save workflow. | Keeping the bulk editor on the user selection route. |
| 2026-10-21 | `/settings/users` is a searchable selection directory. All user creation, editing, account actions, and permitted pay setup happen on tabbed `/settings/users/new` or `/settings/users/:id` detail pages, with one Save per user. | The read-only detail page and separate `/settings/users/manage` bulk editor in the preceding decisions. |
| 2026-10-21 | Billing positions have an optional, case-insensitive unique local ID for ordering and filtering; their UUID remains the relational key used by users and pay table rates. | Sorting and identifying billing positions by name alone. |
| 2026-10-22 | V5 invoices are D1 records with task lines, source entry allocations, payments, notification history, and provider sync state. Project invoice summaries read these records. An allocation reserves an approved source entry and is finalized on send; the legacy `project_invoice_refs` and entry `invoice_id` fields are dormant. | The earlier read-only invoice reference hook and T&M-only future invoice pool. |
| 2026-10-22 | At 09:00 New York time on the 10th, the API creates one draft per project and month from approved, unallocated prior-month and older T&M, NTE, and fixed fee entries, then notifies the assigned PM. The UTC cron pair is gated by New York local time. Assigned PMs may also create multiple manual invoices for their project and reserve selected entries immediately. | Invoice numbering awaiting a workflow and prior T&M-only invoice pool eligibility. |
| 2026-10-22 | Draft reviewers can bill, write off, or split each entry by hundredth-hour or saved client charge; the complement is written off. NTE charges respect the task's remaining contract amount. Fixed fee time appears in review automatically, while the reviewer sets its task amount within the remaining contract balance. | Automatic billing of fixed fee hours by hourly charge. |
| 2026-10-22 | Assigned PMs manage their projects' drafts and sending; invoice staff have cross-project access and may record partial payments. Sent public invoices use opaque tokens, server-created Stripe checkout, signature-verified webhook confirmation, and a shared PDF renderer. D1 stays authoritative; Brevo and QBO outcomes and retries are visible. | V4's shared docs-host invoice and payment flow. |
| 2026-10-23 | Assigned PMs and invoice staff can permanently delete an invoice while it is a draft. Deletion removes its lines, notifications, events, and entry allocations in one guarded transaction, making the entries available again; a minimal deletion action remains in the general audit log. Invoice numbers are not rewound or reused; sent invoices cannot be deleted. | Retaining draft invoices with a `void` status. |
| 2026-10-23 | The V5 client invoice PDF follows the V4 invoice layout but uses V5 line and payment fields. Manage and Payment share one renderer. The company name and preferred rectangular (or square fallback) logo come from current company settings; staff logo access follows invoice permissions, and public logo access requires a sent or paid invoice token. | V4's hardwired invoice logo and the initial V5 text-only PDF. |
| 2026-10-23 | New manual invoices select available approved time by default while retaining an explicit blank-draft action. An existing draft can reserve additional approved time without changing its number. Manage recalculates billed hours, write-offs, time charges, and the invoice total before Save as decisions change. Fixed fee invoice amounts initially follow billed time charges and subsequent decisions, capped at the remaining task contract amount. A PM may override the suggested amount to bill ahead of worked time, but cannot exceed the remaining contract amount. | The initial blank-by-default manual invoice form, saved-only review figures, and manager-entered-only fixed fee amounts. |
| 2026-10-23 | Stripe payments export to QBO at their confirmed gross amount with a named Stripe PaymentMethodRef, the configured deposit account, the confirmed payment date, and an invoice link. The Stripe intent/session ID is kept in the private note. QBO project customers inherit the client billing address; the invoice also carries its billing address snapshot. Missing QBO method or deposit configuration fails visibly for retry rather than allowing QBO to show Cash. | The initial payment export omitted payment method and deposit references and synced project children with empty billing addresses. |
| 2026-10-23 | Manage and Payment development commands launch the local API and a Stripe CLI listener together. The launcher obtains the CLI signing secret and passes it to Wrangler for verified local webhooks; it uses a test API key from local API configuration. The root Manage command continues to start both front-end apps. | Starting either front-end without webhook forwarding or a matching signing secret. |
| 2026-10-23 | Current client, contact, and project API routes and shared contracts live in domain files. Task, timesheet, and invoice contracts or routes retain their domain owners. The historical QuickBooks-backed project-management contracts are split into legacy domain files with a retained export surface. Existing `/records` URLs remain valid. | Grouping unrelated domain behavior in `recordsApi.ts`, `records.ts`, or the legacy `projectManagement.ts` implementation. |
| 2026-10-23 | V5 pages and active consumers define the feature scope. Unused V4-backed contracts, mappers, routes, page copies, redirects, and assets are removed. V4-only GIS, review packages, and account reporting stay in `V5_REVIEW_REGISTER.md` pending a new product decision. Shared contracts are kept only when active V5 code on both sides uses them; D1 row shapes stay local. | Retaining V4 project-management and GIS definitions as a future V5 export surface. |
| 2026-10-23 | Main contact and career applications submit to V5 public endpoints. The API owns `info@whitepointsurvey.com` as the contact and application inbox and sends a contact acknowledgement to the supplied sender email through one Brevo transport. Docs favorites use authenticated V5 D1 storage. | Browser-exposed V4 transaction-email credentials, placeholder career application, and the non-existent favorites endpoint. |
| 2026-10-23 | The cleaned local D1 baseline removes dormant project invoice references, timesheet invoice flags, and redundant project status and cost columns. Current invoices use allocation rows and project actual cost derives from approved time; QBO project move history stays. Local D1 was reset for validation. | The prior dormant invoice field retention and status duplication. |
| 2026-10-23 | `dev:manage` starts Manage, API, and the Stripe CLI listener; `dev:payment` starts Payment, API, and the listener. The launcher passes its test-mode webhook signing secret to Wrangler. | The earlier root Manage command that also started Payment. |
